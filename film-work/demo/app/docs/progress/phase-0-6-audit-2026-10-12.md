## 2. Phase 7, in flight: the JavaScript budget is met, and the user pays more JavaScript

The uncommitted work (25 modified/deleted files, 17 untracked paths) implements Tasks 1–3 of
`docs/superpowers/plans/2026-10-10-catalog-js-reduction.md`: `/catalog` moved from the App Router to the
Pages Router (`src/pages/{catalog,_app,_document}.tsx`), brand symbols moved to server rendering, catalog
icons replaced by a static SVG sprite, and `build` switched to `--webpack`. Every checkbox in that plan is
still unticked and Task 4 (record the outcome) is not done.

Measured today, with the project's own gate (`scripts/check_phase7_js_budget.ts`) against a sanitized
built workspace and the large fixture database:

| Tree | Bundler | First-load JS (gzip 9) | Gate <120,000 | Extra JS during catalog journeys |
| --- | --- | --- | --- | --- |
| Committed `HEAD` (App Router catalog) | turbopack | 168,608 | fail | 3,886 |
| Working tree (Pages catalog) | **webpack** | **118,706** | **pass** | **144,304** |
| Working tree (Pages catalog) | turbopack | 136,589 | fail | 146,538 |

Working-tree first-load breakdown: `framework` 59,603 · `main` 40,282 · `catalog` 10,302 · `_app` 6,268 ·
`webpack` 1,718 · manifests 533. HTML 16,952 gzip. The icon sprite is a separate 7,910-byte image response.

Three facts follow from this table.

1. **The gate passes with 1,294 bytes of headroom (1.1%).** Any future client-side addition to the catalog
   breaks it again.
2. **`--webpack` is load-bearing.** The same tree built with the default bundler misses the budget by
   16,589 bytes. Nothing in the repo records this; the existing `catalog-js-turbopack.json` /
   `catalog-js-webpack.json` pair compared bundlers on the *App Router* catalog, where webpack was slightly
   worse (169,980 vs 168,732). Also note `dev` still runs turbopack, so development and production now use
   different bundlers.
3. **Total journey cost rose.** On the committed tree, filtering, sorting, paginating, comparing and
   toggling the theme pulled 3,886 further gzip bytes. On the working tree the same journeys pull 144,304 —
   App Router chunks (`142-…`, `70848e81-…`, `main-app-…`, `layout-…`, `page-…`) fetched because links and
   prefetches now cross a router boundary. A visitor who filters and opens one offer downloads
   ~263,010 gzip bytes of JavaScript, against ~172,494 before: **+52%**.

The Pages Router catalog meets the defined first-load target with webpack, but crossing to App Router pages downloads another runtime. This is a measured tradeoff, not a reason to change the budget denominator.

Decision for these prerequisite repairs: preserve the existing catalog work, verify navigation, disclosure, nonce protection, recovery and shared-shell behavior, and publish both first-load and later-script totals. Do not undo user work or relax the strict threshold without a separate architecture decision.

The shell uses the existing `SiteFrame`, header and footer; the two router entry points still need separate font/document setup. Existing fixture-based tests already invoke `src/pages/catalog.tsx`. The repair adds a real publication/private-cache regression and exercises both shells in the packaged app rather than adding a test of copied markup.

Route parity of the migration itself is otherwise good: the Pages route reuses `getPublicCatalogState`,
`createCatalogPage`, `encodeCatalogRows` and `CatalogClient` unchanged, and adds canonical/OG metadata the
deleted App route never had.
