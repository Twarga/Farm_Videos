# bestvpsforme application audit — 31 August 2026

This audit covers the current public routes, responsive behavior, catalog interactions, offer and provider pages, admin entry points, design-system consistency, accessibility basics, data readiness, and the proposed editorial/SEO surface.

## Executive decision

The frontend is a credible product foundation, but the application is not ready for public production traffic yet.

The interface has a recognizable point of view, the catalog works, the public routes build cleanly, and the layout does not create page-level horizontal overflow at the tested desktop and mobile widths. The urgent work is data truth, mobile usability, admin integration, and removal of stale prototype details—not another full visual redesign.

## The good

- The product has a clear promise: expose price, place, hardware, and the catch before sending a user to a provider.
- The crimson, white, near-black, IBM Plex Sans, and IBM Plex Mono system is recognizable without looking like a generic hosting template.
- The catalog supports search, filtering, sorting, list/card views, comparison, provider pages, and individual offer pages.
- Provider logos and flags make dense information easier to scan.
- Public layouts were tested at 1280 × 720 and 390 × 844 without page-level horizontal overflow.
- Light and dark themes, focus-visible styling, and reduced-motion handling are present.
- Methodology, privacy, corrections, updates, sitemap, robots, canonical metadata, and offer structured data already create a strong trust foundation.
- Lint and the production build pass on Next.js 16.3.3.

## The bad

### 1. The public data is not one source of truth

The application currently has:

- 2 database seed offers;
- 33 curated offers used as a development fallback;
- 457 CSV rows across 63 providers in `data/vps-offers-2026-08-31.csv`.

The CSV check also reports one blocking row error and six warnings. Until the reviewed database publication becomes the only public source, a successful-looking frontend can hide an incomplete production catalog.

**Fix now:** resolve the CSV error, review warnings, map all valid provider identities/logos, stage the import, publish to a local production-like database, and remove the development fallback after verification.

### 2. Mobile catalog scanning is exhausting

At 390 px wide, the 33-offer catalog is roughly 8,000 px tall. The page works, but finding and comparing plans requires too much scrolling.

**Fix next:** add a compact mobile row, show only the highest-value facts by default, move secondary facts into an expandable detail area, keep active filters visible, and paginate or progressively reveal results.

### 3. Interactive targets are too small

Navigation, theme, filters, segmented controls, compare actions, footer links, and several admin controls are commonly 28–40 px tall. They should normally provide at least a 44 × 44 px touch area on mobile, even when the visible icon remains small.

### 4. A catalog search field has no programmatic label

Its placeholder is not a replacement for a label. Add a visible or screen-reader-only label and connect it with `id`/`htmlFor` or `aria-label`.

### 5. The provider detail hierarchy is invalid

The provider page currently renders two `h1` elements. Keep the provider identity as the single `h1`; make “plans” an `h2`.

### 6. Public freshness text is stale

Some public components still say “27 Aug 2026,” while the active source file is dated 31 August 2026. Publication dates must come from the published snapshot, not component text.

### 7. The development CSP creates a visible error badge

The browser console reports that React development mode requires `eval`, while the CSP blocks it. Keep the strict production CSP, but use a development-only policy that supports the framework's development runtime. Then verify that production still excludes `unsafe-eval`.

## The ugly

### 1. The polished admin and the real import workflow do not feel like one product

The main admin presentation uses the design system, while the authenticated import page and login use large inline-style blocks and hard-coded colors. The result is inconsistent dark mode and an operational workflow that looks detached from the dashboard.

**Required change:** place login, import preview, issue resolution, publish, rollback, and snapshots inside the same admin shell and token system. The secure server actions remain; only the presentation and navigation need consolidation.

### 2. Prototype language and code remain after the product direction changed

The Finder is hidden and redirects to the catalog, but Finder events, components, analytics labels, tests, and plan references remain. This is not a launch blocker, but it creates maintenance noise and misleading dashboard metrics.

### 3. The plan and implementation state disagree

The detailed implementation plan still describes completed database, auth, analytics, and framework-upgrade work as blockers. `docs/archive/PROJECT_PROGRESS.md` is newer. The plan should be maintained as the architectural reference and the progress board as current evidence.

## Homepage section review

The “Four checks before any recommendation” section is clean, but it feels unfinished rather than intentionally minimal.

### What works

- The four-part mental model is easy to understand.
- The section supports the product's transparency promise.
- The lack of containers avoids the box-inside-box problem from earlier designs.

### What weakens it

- The body copy and icons are too small relative to the available space.
- The vertical gap before “What listicles skip” is excessive.
- Both groups repeat the same icon + label + sentence rhythm, so the second group feels redundant.
- “Listicles” is insider language; a beginner may not know or care what it means.
- There is no clear next action before the footer.

### Recommended composition

Use one tighter section titled **The details we never hide**.

First row:

- **Price** — Monthly price, cash due today, and renewal.
- **Location** — Countries and cities where the server actually runs.
- **Hardware** — CPU type, RAM, storage, and bandwidth in plain English.
- **The catch** — Limits, missing extras, and support risk.

Second row should be a quieter proof strip rather than four equal feature blocks:

- **Cash due:** What you pay today—not the teaser price.
- **Trustpilot:** A dated snapshot, not a live rating.
- **Affiliate:** Clearly labeled and never used to rank plans.

Finish with **Browse 33 checked offers →**. Increase supporting copy to 15–16 px, icons to 20–22 px, reduce the section's unused vertical space by about one third, and preserve the border-free layout.

## Blog recommendation

Call the public section **Guides** or **Research**, not “Blog.” The goal is SEO acquisition, beginner education, and evidence-backed trust—not a stream of company announcements.

Start with local MDX files. This is the cheapest and simplest option for one owner: content is versioned, reviewed in pull requests, included in backups, and requires no CMS service. Add a database editor only after publishing through Git becomes a real burden.

### Initial information architecture

- `/guides` — one featured guide, topic filters, and a compact article list;
- `/guides/[slug]` — article pages;
- `/about` or `/authors/[slug]` — author experience and editorial policy;
- `/feed.xml` — RSS feed;
- guide links inside relevant offers, providers, methodology, and prefiltered catalog views.

### Content groups

1. **Beginner foundations:** VPS versus shared, cloud, and dedicated hosting; vCPU; RAM; NVMe; bandwidth; managed versus unmanaged.
2. **Workload guides:** n8n, Coolify, WordPress, VPN, game server, and small SaaS requirements.
3. **Honest comparisons:** dated provider comparisons using the same price and caveat model as the catalog.
4. **Dataset research:** monthly price movement, provider coverage, renewal terms, IPv4 charges, and offer changes.
5. **Founder and trust notes:** methodology, affiliate independence, corrections, and how research is performed.

### First eight articles

1. What is a VPS? A beginner's guide
2. VPS vs shared hosting vs cloud vs dedicated server
3. How much RAM do n8n, Coolify, and WordPress need?
4. Why a cheap VPS price can be misleading
5. Hetzner vs netcup for a first European VPS
6. What 457 VPS offers reveal about the 2026 market
7. How bestvpsforme ranks plans without using affiliate commission
8. How to choose the right server location

### Article quality contract

Every article must have a named author, publication and update dates, source links, the data-snapshot date, methodology or testing notes where relevant, a visible affiliate disclosure, a useful catalog action, and related guides. Do not mass-publish thin AI pages. Six excellent, maintained guides are more valuable than fifty interchangeable summaries.
